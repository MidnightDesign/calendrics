# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Until 1.0.0 the public API may change between minor versions.

## [Unreleased]

### Added

- **`toLocaleString()` on the porcelain layer.** `Temporal\PlainDate`, `PlainDateTime`, `PlainTime`, `PlainYearMonth`, `PlainMonthDay`, `Instant`, and `ZonedDateTime` can now render themselves the way a human in a given locale would write them. Where ECMA-402 passes an untyped options bag, the porcelain signatures are typed named arguments, and each type exposes only the options that apply to it — `$plainDate->toLocaleString(timeStyle: …)` and `$plainYearMonth->toLocaleString(day: …)` are compile errors rather than the runtime `TypeError` the spec raises. Six enums back the options: `FormatStyle`, `TextWidth`, `NumberWidth`, `MonthWidth`, `TimeZoneNameStyle`, and `HourCycle` (which collapses ECMA-402's overlapping `hour12`/`hourCycle` pair). `Duration` is deliberately excluded — localized duration output needs `Intl.DurationFormat`, which `ext-intl` does not expose. All formatting delegates to the spec layer, so the ECMA-402 calendar-compatibility and style-conflict rules validated by test262 apply unchanged.
- **`fromDateTime` / `toDateTime` on porcelain value types.** Native `\DateTimeImmutable` interop for `Temporal\Instant` (both directions, optional `\DateTimeZone` arg, defaults to UTC), `Temporal\ZonedDateTime` (both directions, preserves the zone id), and `fromDateTime` on `Temporal\PlainDateTime`, `Temporal\PlainDate`, `Temporal\PlainTime`. Sub-microsecond Temporal bits are zero on conversion (PHP's `\DateTimeImmutable` is microsecond-precision). Unblocks "wrap your own clock" testing without a library-blessed clock-injection seam — see issue #19 for rationale.
- **`Temporal\Exception\` hierarchy.** Introduces a `TemporalException` marker interface and concrete classes (`InvalidArgument`, `RangeError`) that extend the corresponding SPL parents (`\InvalidArgumentException`, `\RangeException`). Porcelain throw sites in `Calendar::fromId()` and `RoundingMode::{to,from}PhpRoundingMode()` now throw `Temporal\Exception\InvalidArgument`; existing `catch (\InvalidArgumentException)` / `catch (\LogicException)` clauses keep working because the SPL parents are preserved. The marker interface lets consumers catch every Temporal-origin throwable through a single base. Spec-layer throw sites still emit bare SPL exceptions and will be retrofitted onto this hierarchy in subsequent minors.

### Fixed

- **An exact `PHP_INT_MAX`/`PHP_INT_MIN` epoch value was mistaken for the clamp marker of an over-int64 one.** `Instant` and `ZonedDateTime` hold an instant as the public int `epochNanoseconds` field plus a carried `(epochSec, subNs)` pair, and the field saturates to `PHP_INT_MIN`/`PHP_INT_MAX` once the true value stops fitting int64. The pair was carried *only* when it saturated, so a legitimate `PHP_INT_MAX` nanosecond count — 2262-04-11T23:47:16.854775807Z, an unremarkable in-range instant — was indistinguishable from a clamp, and `new Spec\ZonedDateTime(PHP_INT_MAX, 'UTC')->add(Duration::from('PT1H'))` refused with "arithmetic result is outside the representable range" for a result three centuries inside it. The pair is now carried for every instant, so the field is a display value that nothing has to interpret, and the conservative guard in `Internal\ZonedArithmetic` that raised that `RangeError` is gone. Two more consequences of the old shape go with it. Decomposing the field flooring toward −∞ overflowed on the way back — `PHP_INT_MIN` floors to −9_223_372_037 s, whose nanosecond product is past `PHP_INT_MIN` — so the remainder degraded to a float and lost its low digits: `new Spec\Instant(PHP_INT_MIN)` rendered `…:43.14522368Z` instead of `…:43.145224192Z`, and `epochMilliseconds` and `add()` raised `TypeError` on the float that leaked out of it. And `Spec\ZonedDateTime::from($zdt)` rebuilt its copy from the clamped field rather than the carried pair, silently moving an over-int64 argument to 2262 instead of reproducing it.
- **Object property bags were read with `get_object_vars()`, so anything exposing its fields through `__get` came through empty.** Every spec-layer entry point that takes a property bag or an options bag — `from()`, `with()`, `toPlainDate()`, `round()`, `total()`, `until()`, `since()`, `toString()`, `toLocaleString()`, `getTimeZoneTransition()`, and Duration's `relativeTo` anchors — snapshotted object arguments with `get_object_vars()`, which sees only *declared public properties*. An ordinary PHP DTO, a lazily-hydrated entity, or a wrapper around a config array would silently yield no fields at all: `Spec\PlainDate::from($dto)` threw "property bag must have a year field" for a `$dto` that reports `year`, `month` and `day` perfectly well, and an `overflow`/`smallestUnit`/`relativeTo` option supplied the same way was ignored rather than honored. Bags are now read one property at a time through the faithful TC39 `Get(O, P)` (`Options::bagGet()`, which already existed and was used at two sites), so accessor-backed objects work. Arrays and plain `stdClass` bags are unaffected.
- **Property-bag fields are now read in the order TC39 prescribes, and only the fields the operation actually recognizes.** `PrepareCalendarFields` reads `calendar` first, then the calendar's field list sorted alphabetically, with `era`/`eraYear` present only for calendars that have eras — which matters once reads are observable, because an accessor may throw, and probing a field the spec never reads would invent an error. `with()` bags additionally read `calendar`/`timeZone` — with a `Get`, ahead of every other field, as `IsPartialTemporalObject` prescribes — so an accessor for either name fires, and fires first.
- **`ZonedDateTime` raised `\TypeError` instead of `Temporal\Exception\RangeError` for epoch magnitudes past int64 seconds.** The `@internal` true-epoch-parts seams (`fromInstantParts()` / `createFromEpochParts()`) declared `int` parameters, so a seconds count too large for int64 — 2¹²⁸ nanoseconds, for instance — failed on the parameter type before the range check could run. `Instant::fromEpochParts()` already narrowed such values to a `RangeError`; both classes now share that narrowing via `EpochValue::narrowParts()`. Surfaced by test262's `ZonedDateTime/limits.js`, which the transpiler previously could not express.
- **`ZonedDateTime::getTimeZoneTransition('next')` could return a transition in the past.** When a zone had no transition left in the 200-year search window, the `next` branch fell through into the `previous` search instead of returning `null`, so `Asia/Riyadh` at 2024 reported its 1947 LMT-to-standard transition as its *next* one. Zones with DST were unaffected — the fall-through only happened once the forward scan found nothing.
- **`dayOfWeek` was wrong for every date at ISO year ≤ 0.** The ISO weekday used Sakamoto's algorithm with PHP's truncating `intdiv()` and `%`, both of which round toward zero rather than flooring, so negative years got a wrong leap-day count and a negative remainder — `dayOfWeek` could return values outside its documented 1–7 range. It is now derived from the Julian Day Number, which the codebase already computes with floor division. `weekOfYear` and `yearOfWeek` are fixed with it, as is `dayOfWeek` on `PlainDateTime`/`ZonedDateTime` and on the porcelain types that delegate to them. Surfaced by test262's `intl402/PlainDate/from/hebrew-keviah.js`, which walks Hebrew years 3700–5800 (ISO −61 onward) and now passes for all 2101 of them.
- **`toLocaleString()` ignored the value's calendar.** A Hebrew-calendar `PlainDate` formatted with an `en-US` formatter rendered as a Gregorian date, silently reinterpreting its fields. Per ECMA-402 it now throws `Temporal\Exception\RangeError` unless the value's calendar matches the formatter's resolved calendar. `PlainDate`, `PlainDateTime` and `ZonedDateTime` still accept the ISO 8601 calendar against any formatter; `PlainYearMonth` and `PlainMonthDay` do not, matching the spec — a bare year-month or month-day has no meaning outside its own calendar, so `(new Spec\PlainYearMonth(2000, 5))->toLocaleString()` now throws where it previously returned a Gregorian rendering.
- **`toLocaleString()` ignored a locale's default calendar.** Locales that select a non-Gregorian calendar without a `-u-ca-` keyword — `th-TH` → `buddhist` is the common case — formatted in the Gregorian calendar. `th-TH` now renders 2000-05-02 as `2/5/2543`, matching `Intl.DateTimeFormat`.
- Spec-layer `toLocaleString()` now throws `Temporal\Exception\TypeError` for inapplicable style options instead of a bare `\TypeError`. The SPL parent is unchanged, so existing `catch (\TypeError)` clauses keep working.
- **Options were all read before any of them was coerced.** TC39 reads each option and applies its `ToString` immediately, then moves to the next; the spec layer snapshotted the whole bag first and coerced later, in whatever order the consuming code happened to want. The difference is observable whenever a bag supplies its options through accessors: a getter that throws could pre-empt the `RangeError` an earlier, already-read option was going to raise. `Options::bagSnapshot()` now coerces each string-valued name as it reads it.
- **A property bag could not supply `monthCode`, `era` or `offset` as a `Stringable`.** TC39 reads those fields with `ToPrimitiveAndRequireString`, so any value that renders itself as a string is legitimate input, but the implementation required a native `string` and raised a `TypeError`. (`calendar` and `timeZone` still require a real string — `ToTemporalCalendarIdentifier` and `ToTemporalTimeZoneIdentifier` demand one rather than coercing.)
- **The options argument was type-checked before the operation's primary argument was converted.** `since()`, `until()`, `add()`, `subtract()`, `toString()` and friends declared `array|object|null $options`, and PHP validates a typed parameter *before* the method body runs — so a primitive options argument raised its `TypeError` while the `other`/`duration` property bag went unread. TC39 converts that argument first, accessors and all, and only then reaches `GetOptionsObject`. The parameter is now `mixed` (as `from()` and `with()` already were) with the check moved inside.
- **`with()` read its options after deciding whether the fields describe a real date.** TC39 orders the three steps *prepare fields → read options → validate against the calendar*, so `plainDate.with({ monthCode: 'M08L' }, options)` reads `options.overflow` before rejecting the leap month code that the ISO calendar has no room for. All five `with()` implementations now split field preparation from calendar validation. Non-positive `month`/`day` values stay in the first group: they are rejected by `ToPositiveIntegerWithTruncation` during preparation, not by the calendar.
- **`from()` read its options before the property bag.** `PrepareCalendarFields` precedes `GetOptionsObject`, so a bag's accessors run — and can throw — ahead of any complaint about the options argument. Fixed for `PlainDate`, `PlainYearMonth`, `PlainMonthDay` and `ZonedDateTime`.
- **`ZonedDateTime::from()` read options before parsing a string, and read some of them twice.** A malformed ISO string must be a `RangeError` before an options accessor is touched; instead the options were resolved up front, and the string branch then re-normalized the raw bag, firing every accessor a second time. `overflow` was additionally coerced twice on the property-bag branch. `Instant::toString()` had the same double read of `timeZone`, left over from a workaround for `get_object_vars()` that a faithful `Get(O, P)` made unnecessary.
- **`PlainMonthDay::toPlainDate()` probed `era` and `eraYear` on ISO-calendar values.** `PrepareCalendarFields` uses the receiver's calendar, and an eraless calendar has no such fields — reading them fires accessors for names the spec never touches.

### Changed

- **Leftovers from the `PlainDateTime` split.** The split deduplicated `PlainDateTime`'s own copy of the as-if-positive nanosecond rounding into `EpochRounding::roundAsIfPositive()` but left the byte-identical private copy in `PlainTime` untouched; it is gone now, and both `PlainTime` call sites delegate to the shared method. The ns-per-unit constants tell the same story one level down: `NS_PER_DAY`/`NS_PER_HOUR`/`NS_PER_MINUTE` (and the millisecond/microsecond pair under their abbreviated names) were redeclared privately in `PlainDateTime` and again in three of the four new collaborators, while `EpochLimits` already owned the second/millisecond/microsecond constants — all five now live once on `EpochLimits`. Mago's complexity ratchet also moves down again: `cyclomatic-complexity` 300 → 250 and `kan-defect` 20.0 → 15.0, sitting just above what the code now measures (the `Duration` value type at 248, `IntlCalendarBridge` at 14.91) after the split took the previous front-runner out of the running.
- **`Temporal\Spec\PlainDateTime` split into a value type and four named internal collaborators.** At 2,546 lines it was the largest file left in the repository — the same shape `Duration` and `ZonedDateTime` had before their splits: the datetime value type, the ISO-string grammar, the property-bag constructor, the add/subtract engine and the `since`/`until` engine all shared one file with no seam between them. The public API is unchanged — `add()`, `subtract()`, `since()`, `until()` and the string/bag branches of `from()` are now one-line delegations — but the machinery moved into `Temporal\Spec\Internal\{DateTimeParse, DateTimeFields, DateTimeArithmetic, DateTimeDifference}`, and `PlainDateTime` itself is down to ~1,280 lines. Duplication went with the move: the time-fields↔nanoseconds conversions became `CalendarMath::{timeToNs, nsToTime}`, and `PlainDateTime`'s private `roundPositiveNs()` copy was deleted in favor of `EpochRounding::roundAsIfPositive()` (identical mode table and halfEven tie-break). The unrelated PHP-interop helper that previously held the `DateTimeFields` name (epoch-ns ↔ `\DateTimeInterface`, used only by the porcelain layer) is renamed `PhpDateTimeInterop`, so the field-construction collaborator's name lines up with `ZonedFields`. Behavior is byte-identical: all PHPUnit tests pass with the same incomplete count as before.
- **Two leftovers from the `ZonedDateTime` split.** The split deduplicated the fractional-second rule into `Internal\IsoFraction` but left the UTC-offset rule beside it in two byte-identical copies — `Instant` and `Internal\ZonedParse` each carried the same ~50-line scanner, differing only in `Instant`'s range check — so the offset lexeme now has its own `Internal\IsoOffset`, with that check staying at the call site whose error names the string it came from. Both copies declared the scan as returning `int<0, 86399>`; the grammar matches two digits per component and so admits `+99:99:99`, which is 100 hours, and the annotation was papering over it. `ZonedDateTime` also still answered to three names for one factory — `fromInstantParts()` and `createFromEpochParts()` were pure pass-throughs to a private `fromEpochParts()` — now a single `@internal` `fromEpochParts()`, matching `Instant`'s name for the same operation; the test262 transpiler emitted one of the old names, so it was updated and the affected scripts regenerated. An orphaned docblock fragment left in `ZonedDateTime` by the extraction is removed with them.
- **`Temporal\Spec\ZonedDateTime` split into a value type and five named internal collaborators.** At 4,135 lines it was the largest file in the repository by 60%, and the same shape `Duration` had before its own split: the zoned value type, the ISO-string grammar, the property-bag constructor, the time-zone offset tables, the add/subtract engine and the `since`/`until` engine all shared one file with no seam between them. The public API is unchanged — `add()`, `subtract()`, `since()`, `until()` and the string/bag branches of `from()` are now one-line delegations — but the machinery moved into `Temporal\Spec\Internal\{ZonedParse, ZonedFields, ZoneOffsets, ZonedArithmetic, ZonedDifference}`, and `ZonedDateTime` itself is down to 1,915 lines. Three duplicated or vestigial implementations went with it: the two UTC-offset resolvers (`resolveOffsetSecondsAt` and `staticResolveOffset`) were the same lookup written twice, one of them without the `DateTimeZone` cache, and are now a single `ZoneOffsets::offsetAt()`; `parseSimpleOffset()` was a wrapper whose two branches both duplicated `parseOffset()`; and the per-class `resolveOverflowOption()` wrapper `Options::overflowFromBag()`'s own docblock already asked callers to stop writing. Two new named concepts came out of the move: `Internal\DateSpan`, the calendar portion of a difference, which previously travelled as four parallel `int`s through five signatures; and `Internal\IsoFraction`, the fractional-second rule, which was copy-pasted verbatim into `Instant`, `PlainTime`, `PlainDateTime` and `ZonedDateTime`. Behavior is byte-identical: all 12,396 PHPUnit tests (1,032,288 assertions) pass with the same 311 incomplete as before.
- **Mago's complexity thresholds tightened to match what the code now measures.** `cyclomatic-complexity` drops from 750 to 300 and `kan-defect` from 35.0 to 20.0. Both were set when `Duration` and `ZonedDateTime` scored near 700, with a comment asserting those classes "cannot be split without moving logic across method boundaries the spec keeps together" — which the two splits have since disproved. The highest remaining score is just under 290. The comments now say so, and mark the numbers as a ratchet that should only move down.
- **`Temporal\Spec\Duration` split into a value type and four named internal collaborators.** The class had grown to 4,960 lines and 60-odd private helpers, with `round()` alone spanning 625 of them: the duration value type, the `relativeTo` anchor resolver, the DST-aware day arithmetic, the totalling engine and the rounding engine all lived in one file with no seam between them. The public API is unchanged — `total()` and `round()` are now one-line delegations — but the machinery behind them moved into `Temporal\Spec\Internal\{RelativeTo, AnchorMath, DurationTotal, DurationRounding}`, and `Duration` itself is down to 1,409 lines. Two duplicated implementations went with it: the inlined Richards Julian-Day formula now calls the memoized `CalendarMath::toJulianDay()`, and a private floor-division helper now calls `CalendarMath::floorDiv()`. `Duration::normalizeUnit()` moved to `Options::normalizeUnit()` alongside the other option coercions, and the `relativeTo` field list — read at five call sites — is now owned by `RelativeTo::normalizeBag()`. Behavior is byte-identical: all 12,396 PHPUnit tests (1,030,675 assertions) pass with the same 329 incomplete as before.
- **Spec layer (`Temporal\Spec\`) reframed as a public API layer, not internal.** The 0.1.0 release notes described it as "considered internal"; that was a misframing. The layer is PSR-4 public and will be covered by the Backwards Compatibility Promise on the same terms as the porcelain layer starting at 1.0.0.
- **test262 transpiler folds calls to a fixture's own BigInt helper.** A fixture that computes its epoch arguments — `function epochNsInYear(year) { return (year - 1970n) * avgNsPerYear + avgNsPerYear / 2n; }` — used to abort the whole script, because the helper's intermediates are exactly the magnitudes int64 cannot hold. Such a helper is now recognized as pure and evaluated at transpile time, with every call folded to the value it produces: an over-int64 result lowers to the `(epochSec, subNs)` parts factories, the rest to a plain int literal. Nothing is emitted for the function itself, and a call that cannot fold still bails, so no generated script references an undefined PHP closure. This unlocks the four `year-format` fixtures — the only conformance coverage of `Instant` and `ZonedDateTime` rendering `toString()`/`toJSON()` across the full ±100000-year range: 299 scripts remain incomplete, down from 303.
- **test262 transpiler carries BigInt constants that exceed int64.** A `const` bound to an out-of-int64 BigInt used to abort the whole script; its exact value is now tracked at transpile time and folded into each use — epoch constructions lower to the `(epochSec, subNs)` parts factories, template interpolations to the decimal digits, and a `for…of` over such a table is unrolled. Uses that cannot fold still bail, so nothing references an undefined PHP variable. This unlocks the 17 fixtures that pin down the ±8.64e21 ns epoch boundary, which had no conformance coverage at all: 329 scripts remain incomplete, down from 346.
- The Docker image now places `acorn` in `/node_modules` rather than the global `node_modules`. Node's ESM resolver ignores the global directory, so `composer test262:build` failed to start; `/node_modules` is the nearest directory the image can populate that the `/app` bind mount does not shadow.
- README now has a **Versioning and backwards compatibility** section that spells out the SemVer contract for each layer, the `toSpec()`/`fromSpec()` round-trip guarantee, and the `Temporal\Spec\Internal\` exclusion — resolving the "formal BC policy for the seam" note from 0.1.0.
- **test262's order-of-operations fixtures now assert the order.** The harness's `propertyBagObserver` / `toPrimitiveObserver` were passthrough stand-ins that recorded nothing, and the transpiler dropped every `assert.compareArray` against them — so ~100 fixtures whose entire purpose is pinning down *which* properties an operation reads, and *when*, passed without checking anything. Both observers are now real: `PropertyBagObserver` logs each `Get(O, P)` through `__get` (which the spec layer reaches because it reads bags through a faithful `Get`), and `StringCoercionObserver` logs `ToString` through `__toString`. 353 fixtures now carry 449 live order assertions, which is what surfaced the nine ordering fixes above. JS's `ToNumber` has no PHP hook — no object can stand in for an integer — so numeric coercion stays unobservable and `Assert::compareObserverTrace()` drops the corresponding `…valueOf` events from the expected trace; the property reads around them are compared in full. 18 fixtures also stop being incomplete (337 → 319 on CI; the absolute count is ICU-version dependent, the delta is not).
- test262 transpiler lowers object destructuring in function parameters (`function f({ a, b = 2 } = {}) {}`), which alone was blocking 22 order-of-operations fixtures. It also emits an `ObserverTrace` for a fixture's tracker array, and skips a trace assertion whose call it had to drop, rather than comparing against reads that never happened.
- test262 transpiler distinguishes `{ toString: () => 'str' }` from `{ toString: () => 5 }`. The latter is a wrong-type value only under JS semantics — TC39's `ToPrimitiveAndRequireString` rejects a non-String result, whereas PHP's `__toString(): string` is engine-enforced and always yields a valid string. Such entries are now marked and skipped in throw-asserting tables instead of being lowered into a `\Stringable` that quietly passes.
- test262's probe-bag lowering now throws only for the property the fixture actually probes, instead of for every name not declared on the bag. The old behavior was tied to the spec layer reading bags with `get_object_vars()`; a faithful `Get(O, P)` legitimately reads `calendar` off `{ year, month, get day() { throw } }`, which is not the read those fixtures are watching for.

## [0.1.0] - 2026-04-19

Initial public release.

### Added

- **Porcelain API** (`Temporal\` namespace) — PHP-native facade over the TC39 Temporal spec with strict types, readonly fields, backed enums, and named arguments:
  - `PlainDate`, `PlainTime`, `PlainDateTime`, `PlainYearMonth`, `PlainMonthDay`
  - `Instant`, `ZonedDateTime`
  - `Duration`
  - `Now` (factory for current-time values)
  - Enums: `Calendar`, `Disambiguation`, `OffsetOption`, `Overflow`, `RoundingMode`, `Unit`, plus display-side enums (`CalendarDisplay`, `OffsetDisplay`, `TimeZoneDisplay`, `TransitionDirection`).
- **Spec layer** (`Temporal\Spec\` namespace) — TC39-faithful implementation, exercised by the test262 conformance suite. Considered internal; prefer the porcelain API.
- **ECMA-402 calendar support** — 16 non-ISO calendars (Hebrew, Islamic family, Japanese, Buddhist, Chinese/Dangi, Coptic, Ethiopic family, Persian, ROC, Indian) via `IntlCalendarBridge`, with pure-PHP implementations for Hebrew and Indian.
- **Factory surface per porcelain class** — each class exposes a typed constructor (named arguments supported), a `parse(string)` for ISO 8601 strings, and for the five calendar-aware classes (`PlainDate`, `PlainDateTime`, `PlainYearMonth`, `PlainMonthDay`, `ZonedDateTime`) a `fromFields(...)` named-argument factory covering calendar-specific fields (`monthCode`, `era`, `eraYear`).
- **Interop** — `toSpec()` / `fromSpec()` on every porcelain class for bridging to the spec layer.
- **Test262 conformance** — 6615 passing test262 scripts, 0 failures (~494k assertions).

### Deliberate deviations from TC39

The porcelain layer adapts TC39 semantics to PHP-native conventions rather than mirroring the JavaScript API shape 1:1.

- **No polymorphic `from()` method.** TC39's `Temporal.X.from(string|object)` is not provided at the porcelain level. Use `parse()` for strings and `fromFields()` for calendar fields. The spec layer (`Temporal\Spec\*`) retains TC39-faithful `from()` for anyone needing exact spec semantics.
- **Named arguments, not property bags.** `PlainDate::fromFields(year: 2024, month: 3, day: 15, calendar: Calendar::Gregory)` rather than `PlainDate.from({year: 2024, ...})`.
- **Backed enums, not option strings.** `Overflow::Reject` rather than `{overflow: 'reject'}`.

### Known limitations

- `Duration::round()` and `Duration::total()` throw `NotYetImplementedException` when balancing across calendar units that require a reference point.
- The `Temporal\Spec\` namespace is public PSR-4 but documented as internal; a formal BC policy for the seam will land before 1.0.0.
- Mutation testing currently reports ~72% MSI; see [issue #2](https://github.com/MidnightDesign/temporal-php/issues/2).
